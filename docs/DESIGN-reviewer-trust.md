# 설계안 — 리뷰어 신뢰 가중 (타베로그 모델의 동네 커피 노트 이식)

> 2026-08-13 기획조정실 작성 · CEO 결재 대기. 벤치마킹 C안.
> **이 문서가 승인 범위의 단일 사실 출처다.** 승인 = 1단계(수집)만 착수. 3단계(판정 반영)는 별도 승인.

## 1. 왜 (근거)

- **벤치마크**: 타베로그의 신뢰는 "리뷰어의 이력·전문성으로 평점을 가중"하는 데서 나온다. 신규 계정·과도한 호평은 자동 감쇠.
- **우리 실측 문제**: 결재 #625 — 검증등급 표시 근거 리뷰가 **단일 블로거(업주 자체 계정 추정)** 로 지배되는 사례 확인. 현재는 노출 다양성 캡(표시단)만 있고 **등급 판정 자체는 모든 채택 후기를 동등 취급**한다. 대행사·업주 계정이 여러 글을 쓰면 등급이 과대평가될 구조적 여지.
- **실현 가능성 실측(2026-08-13)**: 노출 후기 표본 1,168건 중 **97%가 blog.naver.com 링크 보유** → 계정 ID 결정론 추출 가능. 리뷰 항목에 `trust`·`score` 필드 이미 존재(합성 파이프라인이 개별 후기 판정을 이미 함).
- **외부 시점**: 2026-07 네이버 영수증 리뷰 29,000건 조작 검거 — 계정 단위 신뢰가 차별화 무기가 되는 국면.

## 2. 신뢰 신호 4종 (전부 결정론 · LLM 없음)

| 신호 | 정의 | 방향 |
|---|---|---|
| ① 경험 폭 | 이 계정이 후기를 남긴 **서로 다른 카페 수** | 많을수록 ↑ (동네 카페를 두루 다니는 실사용자) |
| ② 광고성 이력 | 이 계정 글이 검증 규칙에서 **광고·협찬으로 반려된 비율** | 높을수록 ↓ (체험단·대행 의심) |
| ③ 단독 지배 | 한 카페 채택 후기 중 이 계정 비중(#625 신호의 계정화) | 특정 카페 몰빵 ↓ (업주 자가계정 의심) |
| ④ 활동 분산 | 첫 글~최근 글 기간과 글 빈도 | 단기간 대량 ↓ (캠페인 계정 패턴) |

## 3. 데이터 설계 — `reviewer_profiles` (신규 소형 테이블)

```sql
CREATE TABLE reviewer_profiles (
  rid TEXT PRIMARY KEY,            -- 'naver:{blogId}' (링크에서 결정론 추출)
  cafes_seen INT DEFAULT 0,        -- 서로 다른 카페 수(①)
  accepted INT DEFAULT 0,          -- 채택된 후기 수
  rejected_ad INT DEFAULT 0,       -- 광고·협찬 반려 수(②)
  first_seen TIMESTAMPTZ, last_seen TIMESTAMPTZ,  -- (④)
  updated_at TIMESTAMPTZ DEFAULT now()
);
```

**적재 방식 = 재합성 경로 편승(증분 upsert).** 재합성이 카페 하나를 처리할 때 그 카페에 등장한 계정만 upsert한다 — **추가 전수 스캔 0, 큰 컬럼 재조회 0** (하드룰 준수). 전 카페 프로필은 재합성 순환(8~9일) 한 바퀴에 자연 완성된다. 예상 크기: 계정 수만 행 × 작은 컬럼 ≪ 5MB.

## 4. 가중 공식 (결정론 · criteria 관제 노출)

```
w(계정) = clamp( 1.0
  + min(cafes_seen, 20) × 0.01        // ① 최대 +0.20
  − adRate × 0.5                       // ② 광고반려율 50%면 −0.25
  − (카페내 비중 > 0.5 ? 0.3 : 0)      // ③ 단독 지배 감쇠
  − (활동 7일 미만 & 글 5+ ? 0.2 : 0)  // ④ 캠페인 패턴 감쇠
 , 0.3, 1.3)
```
- 계수는 전부 `criteria`(무배포 조정, L3 키) 등록 — 하드코딩 금지.
- 반영 지점: 등급 산정의 후기 수를 `Σw`(가중 합)로 대체. **개별 후기 삭제·비공개는 하지 않는다** — 가중치는 등급 문턱 판단에만 쓴다(표시 다양성 캡 #625는 그대로 병행).

## 5. 3단계 롤아웃 (관측→검증→반영 · 하네스 규율)

| 단계 | 내용 | 소비자 영향 | 게이트 |
|---|---|---|---|
| **1. 수집** (이번 승인 범위) | 재합성 편승 upsert로 프로필 적재만. 판정 무변 | **0** | 이 결재 |
| **2. 관측** (~2주) | 가중 적용 시 등급이 바뀔 카페 수·명단을 **시뮬레이션 리포트**로만 산출(주 1회, 관제 표출) | **0** | 자동(리포트만) |
| **3. 반영** | 시뮬 결과 CEO 확인 후 실제 등급 반영. `criteria` 스위치 1개로 on | 등급 변동 | **별도 CEO 결재** |

**차단기**: 3단계에서 공개 카페 등급 변동이 시뮬 예측의 ±20% 벗어나거나 검증→참고 강등이 300곳(공개의 ~2%)을 넘으면 자동 중단·보고(기존 대량변동 409 차단기와 같은 정신). **롤백 = criteria 스위치 off 하나**(재합성 불필요 — 가중은 판정 시점 계산).

## 6. 하네스 편입

- `jobContract`: 프로필 upsert는 cron-resynth 계약의 writes에 `reviewer_profiles.*` 추가 선언.
- 원장: 재합성 detail에 `프로필 upsert N건` 표기. 시뮬 리포트는 산출물 신선도 감시(⑦) 대상 등록.
- 효과검증: 3단계 가동 후 "등급 변동 실측 vs 시뮬 예측" 비교를 성공 기준으로(실행≠효과 원칙).

## 7. 비용

| 항목 | 증가분 |
|---|---|
| DB 스캔 | **0** (재합성 편승) |
| 쓰기 | 카페당 계정 ~수십 행 upsert(소형) |
| 저장 | ≪ 5MB |
| LLM | 0 |
| 시뮬 리포트 | 주 1회 소형 집계 |

## 8. 리스크와 정직한 한계

- 구글·유튜브 출처(3%)는 계정 추출이 어려워 **가중 1.0 고정**(불이익 없음).
- 블로그 ID 재사용·양도는 탐지 불가 — ②③④가 부분 보완.
- 오탐 최악 시나리오 = 성실한 동네 주민 계정 감쇠 → 그래서 감쇠 하한 0.3(완전 무시 금지), 표시단은 불변.
